# FML capability matrix

This is the checkout's single capability index. It lists implemented scope, execution/ownership contracts and source-linked regression examples. **A linked test indicates coverage, not that every row was rerun in the current change or validated for every cosmology/production scale.** The [build/API guide](BUILDING.md) covers shared C++17 requirements and optional dependencies. Module guides remain authoritative for estimators, units, accuracy and exclusions. The [backlog](DEVELOPMENT_BACKLOG.md) tracks pending engineering and science work rather than redefining this matrix.

Dependency entries describe the main workflow: C++17 and linked module implementation objects are implicit; optional branches may add dependencies. “MPI” means the identified API supports collective/distributed work, not that any Python wrapper is distributed. OpenMP support is module/loop specific. Follow catalogue ownership exactly.

## Scope boundaries and validation

- The Python interface wraps the selected serial spatial-statistics workflow. It does not make the C++ MPI APIs callable through Python, replace the legacy wrappers, or expose every template.
- Distributed particle/mesh ownership is distinct from replicated catalogue statistics. The distributed pair-catalogue backend is still backlog item 8; the capability index does not imply it has shipped.
- Deferred KD-tree engineering (22–24), an ultra-light-axion spectral solver, hydrodynamics/Riemann solvers and a BORG/LEFTfield-style forward-model stack remain proposals in the backlog. Existing related primitives do not establish complete implementations.
- Survey-window mixing is different from assignment-window deconvolution; reconstructed displacement fields are different from validated recovery of quasi-real-space positions. Follow each estimator's tests and physical definitions.
- Module regression fixtures, analytic/manufactured cases and external-reference comparisons cover different levels of evidence. Production mock recovery, force/mesh convergence, scientific calibration and application-specific performance remain separate work where the module guide says so.

When adding a capability, update this matrix, link a runnable example/regression and record supported ownership, dependencies and limits. Keep implementation progress in the backlog and detailed estimator/API contracts in their module guides, so this index stays the single discovery table.
